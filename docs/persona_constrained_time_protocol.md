# Persona constrained-time MILP-vs-pipeline protocol

Operationalizes supervisor comment #2: *"Persona-like scenarios + their MILP-to-pipeline comparison in constrained time, with the radar chart of sources of criticity highlighted."*

The cheap deliverables (persona scenario generation + criticity radar) are
already produced. This document is the playbook for the heavy follow-up
(MILP references + 120 s pipeline run + driver analysis), so the same
analysis used for `latent_vs_grid_milp_120_caps_k1` can be reproduced on the
persona families.

---

## 0. What already exists

- `outputs/persona_vre_battery_scenarios/`, `outputs/persona_network_operator_scenarios/`, `outputs/persona_mathematician_scenarios/` — 100 scenario JSONs each, generated by `scripts/generate_persona_scenarios.py`.
- `outputs/personas_criticality_radar/` — radar PNGs (stress, hardness, combined) and `persona_criticality_means.csv` produced by `scripts/build_persona_criticality_radar.py`. **This is the radar of sources of criticity per persona** that the supervisor explicitly asked for.

## 1. Solve MILP references (heavy)

Each persona is shaped to be combinatorially harder or more physically stressed than the standard low/medium/high split, so MILP optimal-objective references are slow. Reuse the standard solver:

```bash
python -m scripts.solve_eval_families \
    --families persona_vre_battery_scenarios \
               persona_network_operator_scenarios \
               persona_mathematician_scenarios \
    --time-limit 1200
```

This populates `outputs/<family>/reports/<scenario_id>.json` with the reference MILP run (objective + solve time). At 1200 s per scenario × 300 scenarios this can take days; consider running per-persona or on Colab/cluster.

## 2. Run the pipeline at the 120 s budget

Reuse the same launcher used for `latent_vs_grid_milp_120_caps_k1`. Locate it (likely `src/uc_jepa/evaluation/evaluate_latent_pipeline.py` or one of the notebook drivers in `notebooks/evaluation_*`) and point it at the persona families. The pipeline run produces a per-scenario PKL/CSV with `pipeline_solve_time`, `pipeline_objective`, etc.

## 3. Build the matched-budget MILP-vs-pipeline table

Re-use `src/eval/time_constrained_milp.py` (matched-pipeline-budget MILP) on each persona family using the pipeline solve times from step 2 as the per-scenario budget. Export the same `matched_budget_per_scenario.csv` schema as `outputs/uc_jepa/latent_vs_grid_milp_120_caps_k1/matched_budget_per_scenario.csv`.

A clean place to land the outputs:
```
outputs/uc_jepa/personas_120_caps_k1/
    matched_budget_per_scenario.csv
    fixed_budget_per_scenario.csv      (optional)
    matched_budget_summary.csv
    ...
```

## 4. Compute components + driver analysis (one command each)

Once step 3 has produced `matched_budget_per_scenario.csv`, the existing scripts work as-is:

```bash
python scripts/build_criticality_components_table.py \
    --input  outputs/uc_jepa/personas_grid_milp_120_k1/matched_budget_per_scenario.csv \
    --output outputs/uc_jepa/personas_grid_milp_120_k1/criticality_components_per_scenario.csv

python scripts/run_criticality_driver_analysis.py \
    --eval-dir outputs/uc_jepa/personas_grid_milp_120_k1
```

This yields the same set of figures and CSVs as the standard low/medium/high analysis, but with `family` ∈ {vre_battery, network_operator, mathematician}. Pair the per-persona win-rate / advantage table with the existing radar to produce the figure the supervisor asked for: **same axes per persona, but two panels — (a) sources of criticity, (b) MILP-vs-pipeline outcome**.

## 6. End-to-end command sequence (grid budgets 1, 2, 5, 10, 30, 60, 120 s)

The launcher `scripts/run_time_constrained_eval_notebook.py` now accepts
`--families-json`, so the only data-side prerequisites are the persona MILP
references (step 1) and the persona pipeline pkl at 120 s (step 2).

The persona-families config file is at `configs/personas_families.json` (already
in the repo). The launcher now takes `--pipeline-results-filename`, so the
mismatch between the notebook default (`*_exact_projection.pkl`) and the
filename `evaluate_latent_pipeline` actually writes (`pipeline_eval_all_families.pkl`)
is handled cleanly.

The AE/JEPA checkpoints are auto-resolved from the latent EBM checkpoint
metadata (`evaluate_latent_pipeline._default_from_checkpoint`), so only
`--latent-ebm` and `--data-root` need to be passed.

```bash
# 1. Solve persona MILP references (HEAVY: hours)
python -m scripts.solve_eval_families \
    --families persona_vre_battery_scenarios \
               persona_network_operator_scenarios \
               persona_mathematician_scenarios \
    --time-limit 1200

# 2. Run pipeline at 120 s budget, k=1 (HEAVY: minutes/scenario)
python -m src.uc_jepa.evaluation.evaluate_latent_pipeline \
    --latent-ebm outputs/uc_jepa/latent_ebm/latent_ebm_best.pt \
    --data-root  outputs/uc_jepa/dataset_train/silver \
    --scenario-root outputs/persona_vre_battery_scenarios \
    --scenario-root outputs/persona_network_operator_scenarios \
    --scenario-root outputs/persona_mathematician_scenarios \
    --output-dir outputs/uc_jepa/latent_time_budget_120_personas_k1 \
    --k 1 --global-time-budget-s 120 \
    --enforce-hard-lp-timeout \
    --selection-policy energy

# 3. Run constrained MILP at the 7 budgets and join with the pipeline
python scripts/run_time_constrained_eval_notebook.py \
    --rerun-milp \
    --hard-timeout \
    --fixed-budgets 1,2,5,10,30,60,120 \
    --families-json configs/personas_families.json \
    --output-dir-name uc_jepa/personas_grid_milp_120_k1 \
    --pipeline-output-dir-name uc_jepa/latent_time_budget_120_personas_k1 \
    --pipeline-results-filename pipeline_eval_all_families.pkl

# 4. Build components + driver tables/figures
python scripts/build_criticality_components_table.py \
    --input  outputs/uc_jepa/personas_grid_milp_120_k1/matched_budget_per_scenario.csv \
    --output outputs/uc_jepa/personas_grid_milp_120_k1/criticality_components_per_scenario.csv
python scripts/run_criticality_driver_analysis.py \
    --eval-dir outputs/uc_jepa/personas_grid_milp_120_k1
python scripts/run_partial_correlation_analysis.py \
    --eval-dir outputs/uc_jepa/personas_grid_milp_120_k1
```

After step 3 the persona-equivalent of `fixed_budget_per_scenario.csv` lives in
`outputs/uc_jepa/personas_grid_milp_120_k1/` with the exact same schema, so the
notebook section 7 (fixed-budget comparison) reproduces all the cross-budget
figures by simply pointing `EVAL_DIR` at this new directory.

## 5. Caveats specific to personas

- The `family` aliases the existing scripts assume are `low|medium|high`. The CSV produced for personas will have other aliases. The component-builder script (`build_criticality_components_table.py`) already falls back to a literal directory match if the alias is unknown, so personas are handled automatically.
- The `mathematician` persona was scored with `alpha = 0.20` (hardness-heavy). When recomputing components for the driver analysis we use `alpha = 0.5` (the default for the standard eval set) to keep cross-family comparison apples-to-apples. The 22 normalized components are unaffected by `alpha` — only the aggregated `criticality_index` is.
- Within each persona, scenarios are deliberately tightly clustered in criticality space (see the `mean ± range` printed at generation time). Within-persona Spearman correlations will be noisier than within-family correlations on the standard set; expect to need persona-level effect sizes rather than Spearman alone.
